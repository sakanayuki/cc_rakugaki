# らくがきバトル

2Dでお絵かきしたキャラクターが3Dで動き出し、NPCと連戦して**5連勝**を目指すWebアプリ。

公開URL: https://sakanayuki.github.io/cc_rakugaki/

設計の詳細は [DESIGN.md](./DESIGN.md) を参照。

## あそびかた

1. **メインメニュー** — あたらしく はじめる／つづきから を選ぶ
2. **オエカキ** — からだ → あたま → りょううで → りょうあし の4ステップで描く
3. **動作プレビュー** — 絵から自動でリグが組まれ、4つのアクションとステータスを確認する
4. **ルーレット** — 通常敵6種＋強敵3種から対戦相手を抽選する（5戦目は強敵のみ）
5. **戦闘** — 自動で戦う。10%で会心の一撃（2倍）。3往復して決着がつかないと必殺技が使える
6. **リザルト** — 勝ち方に応じて強くなる（下記）。5連勝で優勝
7. **殿堂入り** — 5連勝したときだけ。名前をつけて記念写真（JPEG）を持ち帰れる

### 🌐 オンラインたいせん（おともだちと2人で）

動作プレビュー画面の「オンラインたいせん」から入る、**もうひとつのゲーム**。

1. かたほうが **6もじの あいことば**（`DUPAF6` など）を出して、相手に教える
2. もうかたほうが打ち込むと、**端末どうしが直接つながる**（P2P）
3. おたがいの絵を見せ合って、ふたりとも OK なら戦略画面へ
4. **3ターンぶんのグーチョキパー**を先に決める
5. 各ターン、ジャンケンに勝ったほうだけ攻撃できる（あいこは両方）
6. 3ターン終えて、**のこり たいりょくが ％で多いほう**の勝ち。同じならひきわけ

1人用と違うところ:

| | 1人用（5連勝） | オンライン |
| --- | --- | --- |
| 攻撃属性 | 絵から決まる属性 | **戦略画面で選んだ手** |
| 守り属性 | 絵から決まる属性 | 絵から決まる属性（おたがい見える） |
| ターン数 | 最大3往復＋必殺技 | **3ターン固定** |
| 勝敗 | たおしたら勝ち | **のこり たいりょく％** |
| 成長 | 勝つと強くなる | なし（毎回まっさら） |

**選んだ手はジャンケンの手であり、攻撃属性でもある**。

戦略画面には**ぞくせいの かんけいの図**が出る。おたがいの守りの属性と、
「どの手を出されると ダメージ2ばいか」「どの手が相手に こうかばつぐんか」が分かる。
よく効く手には 💡オススメ の吹き出しが付く。

ただし**オススメの手を出せば勝てるわけではない**。それはジャンケンの手でもあるので、
相手に読まれていれば負けて攻撃できない。効かせにいくか、相手の狙いを潰しにいくか ——
そこが読み合いになる（ステータスの数値は見えない）。

### 勝ち方と強くなりかた

上乗せは**初期ステータスに対する加算**で、勝つたびに積み上がる。

| 勝ち方 | 上乗せ |
| --- | --- |
| 3往復以内に相手を倒した | +20% |
| 必殺技で倒した | +10% |
| 👑 強敵に勝った（倒し方は問わない） | +50% |

敵のほうも2戦目から1.1倍ずつ強くなる。強敵はプレイヤーの初期ステータスの1.2倍で、
ルーレットでの面積は通常敵の1/4しかない（引けたらラッキー）。

## 絵からステータスが決まるルール

| パーツ | 影響するもの | ルール |
| --- | --- | --- |
| からだ | ❤️ たいりょく | 塗った面積が広いほど高い（60〜150） |
| りょううで | 💪 こうげき | 塗った面積が広いほど高い（10〜40） |
| りょうあし | 👟 はやさ | 塗った面積が広いほど高い（5〜25） |
| あたま | 属性 | 形で決まる（下記） |

属性は**あたまの形**だけで決まり、じゃんけんと同じ三すくみになる。

- 細長い（縦横比 1.5以上 または 0.67以下） → ✌️ チョキ（ざんげき）
- まるくて塗り密度が高い（0.5以上） → ✊ グー（どんき）
- それ以外 → 🖐 パー（とびどうぐ）

相性は グー→チョキ、チョキ→パー、パー→グー が2倍、逆は0.5倍。

さらに、使ったパレット色の種類数に応じて全ステータスに最大+10%のボーナスがつく。

## 開発

```bash
npm install
npm run dev      # 開発サーバー
npm test         # ロジックの単体テスト（Vitest）
npm run build    # 型チェック + 本番ビルド（dist/）
npm run preview  # ビルド結果の確認
```

### 技術スタック

- TypeScript（strict）+ Vite
- Three.js — ペーパークラフト風の3D表示。描いたパーツをテクスチャ付き板ポリゴンにして関節で回す
- Canvas 2D API — お絵かき（ライブラリ不使用）
- Web Audio API — 効果音をその場で合成（音声ファイルなし）
- localStorage — 絵のセーブ（1スロット）
- PeerJS（WebRTC）— オンライン対戦のマッチングと端末間の直接通信

外部CDN・外部フォントは使わない（ライブラリはすべてnpmでバンドルする）。
**1人用は初回ロード後オフラインで動く**。ネットワークが要るのはオンライン対戦だけで、
`peerjs` もその画面に入ったときに初めて読み込まれる（約87KB / gzip 23KB）。

### 設計上のポイント

- **絵はベクタで保持** — ビットマップではなく描画オペレーション列（`DrawOp[]`）。
  undo・パーツやり直し・保存/復元がすべて「オペを消して再生し直す」だけで成立する。
- **塗りつぶしの境界は全レイヤーの合成画像** — からだの輪郭を境界にして、うでレイヤーを塗れる。
  そのため再生は必ず全パーツ横断で `seq` 順に行う。
- **ロジックはDOM非依存** — `src/game/` と `src/paint/floodFill.ts` は
  Three.jsもDOMも参照しないので、Vitestでそのまま検証できる。
- **敵もプレイヤーと同じデータ形式** — 敵の見た目は `CharacterDoc`（描画オペレーション列）
  として定義してあり、リグ生成・アニメーションのパイプラインを完全に共通化している。
- **絵は必ず分割して送る** — 指で描くと点が桁違いに増え（実測 56,000点 / 圧縮後88KB）、
  1メッセージの上限が64KBの端末では送信が失敗する。しかも片方向だけ黙って届かない形で
  出るので、8,000文字ずつに割って送っている。
- **オンライン対戦は「同じ計算を2台でする」** — 審判役のサーバーがいないので、
  ①ステータスは送らず**届いた絵から各自で計算し直す** ②手は**コミット&リビール**で
  同時公開する ③乱数の種は**両者の値を混ぜて作る**、の3点で成立させている。
  ダメージ計算と乱数の消費順は `battleEngine.resolveAttack()` に1本化してあり、
  1人用とオンラインで共有している（2か所に書くとズレて結果が食い違う）。
- **記念写真も同じ絵から作る** — 殿堂入りの賞状（1080×1080のJPEG）は3Dを使わず、
  保存してあるオペレーション列を描き起こして Canvas 2D で組み立てる（`src/photo/`）。
  保存は Web Share API →ダウンロード→長押し保存の3段構えでフォールバックする。

### オンライン対戦のブローカーについて

「あいことばの人はここにいる」を取り次ぐ受付だけ、**PeerJS の無料公開サーバー**を借りている。
接続が済んだあとは端末どうしの直接通信になり、**絵や対戦データはそこを通らない**。

- 接続先は `src/net/peerConfig.ts` の1か所にまとめてある。
  公開サーバーが止まったら、ここに `host` / `port` / `path` を足して
  自前の [PeerServer](https://github.com/peers/peerjs-server) に向ければ復旧できる
- 直接つながらない回線どうしの中継（TURN）は、PeerJS の既定に含まれる無料のものに
  加えて、`peerConfig.ts` の `EXTRA_ICE_SERVERS` で **TCP・443番でも中継できる先**を
  足している（既定のTURNはUDPの3478番だけなので、UDPを通さない回線で繋がらないため）
- **`peerConfig.ts` に `config`（iceServers）を直接書いてはいけない。**
  PeerJS は `config` を浅く上書きするので、既定値ごと消えて繋がらなくなる。
  足したいときは `EXTRA_ICE_SERVERS` に書くこと
- つながらないときは、画面に出る `ice:failed/failed h3 s1 r0` のような印が手がかりになる。
  `r` が中継（TURN）の候補数で、**`r0` なら中継サーバーに届いていない**

## デプロイ

`main` ブランチへの push で GitHub Actions が起動し、テスト → ビルド → GitHub Pages への
デプロイまで自動で走る（`.github/workflows/deploy.yml`）。

初回のみ、リポジトリ設定で **Settings → Pages → Source** を **GitHub Actions** に
変更しておく必要がある。

公開URLがリポジトリ名のサブパス配下になるため、`vite.config.ts` の
`base: '/cc_rakugaki/'` は必須。これを外すと本番でアセットが404になる。
